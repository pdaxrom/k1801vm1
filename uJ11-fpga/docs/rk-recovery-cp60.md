# CP60: возврат RT-11 после ошибки SD

Файловый загрузчик обнаружил две ошибки прежнего RK611-compatible board.
Они не проявлялись при успешной загрузке RT-11 и DIR. Исправление сохраняет
CPU, FIS, 1002 слова микрокода и контроллер FRAM CP59d. Новый профиль
`--rk-cp60` меняет только выбор private RK service и её PDP-11 firmware.
Это код эмулируемого процессора в прежнем firmware EBR, не микрокод CPU.

## Причина и последовательность

На полном RTL выполняется `UJLOAD.SAV` под исходной RT-11FB V05.03,
с настоящим `DM.SYS`. SD model возвращает error token только для первого
блока данных `ODT.BIN`; SYS/USR/SWAP остаются доступны. Портить все чтения
системного диска для этого сценария нельзя: тогда ОС не сможет завершить
собственный аварийный путь.

1. После первой ошибки RT-11 пишет `002113` в RKCS1 — RECALIBRATE с IE.
   Прежний RTL запускал только READ/WRITE, SELECT и PACK ACK. Запрос
   RECALIBRATE оставался без завершения, ОС ожидала событие.
2. Одного DONE недостаточно: RT-11 различает controller-ready и окончание
   перемещения дисковой головки по DI. Для виртуального диска перемещения
   нет; firmware завершает RECALIBRATE, выставляя DI и DONE, снимая GO и
   сохраняя IE. Вектор `210`, приоритет 5 выдаётся после fixed RTI.
3. После восьми неудачных чтений драйвер записывает `102320` в RKCS1,
   устанавливая CCLR. Старый board трактовал сохранённые IE/DONE как запрос
   нового IRQ. Повторное завершение уже закрытого запроса повреждало
   последовательность обработки I/O в RT-11. Теперь гостевой CCLR имеет
   приоритет над GO/IE/DONE и снимает pending/enable/initialized.
4. Внутренняя firmware пишет в то же EBR слово CERR. Её запись при активной
   private service сохраняет ошибку и ровно один последующий IRQ.
5. При любой ошибке firmware сначала выставляет SD control = 3 (CS high,
   fast mode) и выдаёт один idle byte. Следующее обращение начинает новый
   SPI transaction из определённого состояния.

Семантика сверена с [DEC RK06/RK07 Disk Drive User's Guide,
EK-RK067-UG-001](../../lsi11/docs/EK-RK067-UG-001.pdf): §7.2.1 (GO, RDY, IE,
DI, CERR/CCLR), §7.3 и Figure 7-24 (RECALIBRATE). Воспроизведены реальные
CSR-записи драйвера, а не специальный драйвер для загрузчика.

Модель остаётся прежним подмножеством RK611 для SD: полноценные drive
registers, механические задержки, все positioning/header commands и
RKAS write-one-to-clear этим исправлением не реализуются. DI обслуживает
проверенный путь RECALIBRATE в штатном DM.SYS; это не заявление о полной
совместимости контроллера с любым ПО RK611.

## Реализация и измерения

`build_rk_recovery_cp60.py` берёт точные исходники из архива CP59d и создаёт
изолированный `build/cp60-rk`. Default CP52a, MMU-ветвь и установленный
CP56a остаются прежними. Перед использованием готовой firmware проверяются
SHA-256 её исходника, бинарника и listing. Для пересборки используется
существующий исполняемый assembler; `microasm11` не изменяется.

Firmware RK занимает **348 байт** вместо 320, внутри прежнего EBR.
Возврат остаётся строго по `160476`; аварийный epilogue и RECALIBRATE
расположены после него. Дополнительного EBR, RF или аппаратного процессора
для обслуживания диска нет. Обычный READ/WRITE выполняет три дополнительные
PDP-11 инструкции при входе в service; регистровые CPU loops прежние.

| Gate | LUT | FF | EBR | Slices | Fmax MHz | Итог |
|---|---:|---:|---:|---:|---:|---|
| CP59d | 1239 | 343 | 6 | 624 | 32,531 | Основа, аварийный RK путь неполон |
| CP60a | 1256 | 343 | 6 | 630 | 31,347 | CCLR не исправлен; timing FAIL |
| **CP60b** | **1251** | **343** | **6** | **629** | **32,807** | Полный MAP/PAR/TRACE при 31,824 MHz PASS |

От CP59d: +12 LUT, 0 FF/EBR, +5 slices. Свободны **29 LUT / 11 slices /
1 EBR / 22 слова микрокода**. До исходной цели ≤1100 LUT ещё 151 LUT;
новые аппаратные функции требуют уменьшения площади. Номинальная частота
CPU/SCK остаётся 29,56 MHz. Fmax не является частотой установленной платы.
Прежние допущения о PCB и необходимости физической проверки SCK из CP59
сохраняются; отдельного измерения сигналов платы здесь нет.

Final EDIF: **3146 nets**, нет конфликтующих драйверов и необъяснённых
floating inputs, 7 CIN доказанно не используются; три повреждения netlist
обнаружены. CS output FF по-прежнему находится в PIO и имеет те же
D/clock/enable/preset, что внутренний FF, без нового такта задержки.

## Воспроизведение

```sh
python3 tools/build_rk_recovery_cp60.py
python3 tools/test_rk_recovery_cp60.py
python3 tools/test_service_board_cp60.py
python3 tools/benchmark_board_cp60.py
# На Linux/Diamond, новый каталог gate:
python3 tools/checkpoint_board.py cp60new --rk-cp60 --clock-mhz 31.824 --fram-timing
```

MMIO test проверяет 28 транзакций в portable/vendor моделях: private
RECAL/READ/WRITE, CERR, CCLR/SCLR, IE=0/1, high-byte CCLR, приоритет CCLR
над GO, отсутствие второго IRQ. Возврат старой логики CCLR обязан
завершаться ошибкой теста. Двенадцать прежних service-bank сценариев в
обоих режимах и девять portable/vendor benchmarks проходят.

[Raw CP60a](../synth/reports/cp60a/) и [raw CP60b](../synth/reports/cp60b/)
содержат точные исходники, отчёты, routed NCD/EDIF/PRF.
[Файловый загрузчик и его полный RT-11 test](service-loader-cp60.md).
