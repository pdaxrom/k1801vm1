# CP82: FIS BASIC и переключение программного FPP

2026-09-20 на физической CP67b проверен цикл **FPP включён → выключен →
снова включён**. Исходный DEC `B81FIS.SAV` без адаптера работает корректно,
включая арифметические ошибки, если RT-11 загружена без FPP. Микрокодный
FIS не зависит от программного модуля FP11. `B81FIJ` работает в обеих
конфигурациях; FPU single/double — с включённым FPP.

RTL, микрокод, FPGA FLASH и образы ODT/SDBOOT/FPP не менялись.
Использованы установленный CP80 `FP11.BIN` и BASIC из [CP81](basic-cp81.md).

## Аппаратная проверка

Хост `sash@192.168.1.108`, UART `/dev/ttyUSB1`, 115200 8N1.
Сценарий `tools/hardware_modules_cp82.py` сохраняет исходную таблицу,
находит FPP по установленным BASE/LENGTH/CHECKSUM и проверяет каждую запись
после переключений. Все адреса и статусы ниже восьмеричные.

| Этап | ODT, слот 0 | SDBOOT, слот 1 | FPP, слот 2 |
|---|---|---|---|
| Исходное состояние | 140407 | 140407 | 140407 |
| UJMOD OFF2 | 140407 | 140407 | 140401 |
| Длинный RESET, RT-11 без FPP | 140407 | 140407 | 140401 |
| UJMOD FP11, повторная регистрация | 140407 | 140407 | 140403 |
| Длинный RESET, RT-11 с FPP | 140407 | 140407 | 140407 |

BASE/LENGTH/CHECKSUM всех записей сохраняются. Для FPP это
`060000 004174 142034`; пять пустых записей также не изменились.
Оба холодных старта записаны целиком: свежий banner RT-11 и startup-команды.
Старый prompt не используется как доказательство RESET.

Без FPP отдельно запущены **B81FIS и B81FIJ**. В каждом:

- B81TST: **29 сравнений / 0 ошибок**.
- `PRINT 1/0`: DIVISION BY ZERO, затем READY.
- `PRINT SQR(-1)`: NEGATIVE SQUARE ROOT, затем READY.
- `PRINT 1E30*1E30`: FLOATING OVERFLOW, затем READY.
- `PRINT 2+2`: 4.
- `PRINT 1E-30*1E-30`: FLOATING UNDERFLOW, затем READY.
- Повторное `PRINT 1/0`, затем `PRINT 2+2`: правильная ошибка и 4.

После восстановления FPP повторно проверены **B81FIJ, B81FPU, B81FPD**:
по 29 сравнений, обработка ошибок и дополнительный double-тест — PASS.
Всего в двух конфигурациях выполнены пять сеансов B81TST, один B81DBL
и 29 команд ошибок/восстановления. Последняя таблица точно совпала
с исходной. Плата оставлена в RT-11; picocom восстановлен.

## Семантика конфигурирования

Модульная конфигурация применяется при **холодном старте**:

```text
RUN UJMOD
STATUS
RUN UJMOD
OFF2
```

Затем длинный RESET без ESC. Номер 2 относится к проверенной таблице этой
платы: в другой установке сначала определить слот через STATUS.
OFF снимает AUTO, сохраняя регистрацию, код FRAM и занятый диапазон.
DEL освобождает запись; для временного отключения удаление не требуется.

Возврат FPP в текущем UJMOD:

```text
RUN UJMOD
FP11
```

Затем длинный RESET без ESC. Файл `SY:FP11.BIN` повторно загружается в тот
же слот; loader проверяет данные, bootstrap — checksum и initializer.
Отдельной команды ON в этой версии UJMOD пока нет.

Это не горячая выгрузка из работающей RT-11: изменение таблицы через UJMOD
сначала выключает живые HALT-службы. До RESET прежние флаги обнаруженных
возможностей в RT-11 остаются от старой загрузки; продолжать FP-программы
в таком промежуточном состоянии нельзя. После RESET bootstrap инициализирует
включённые модули, затем RT-11 обнаруживает доступные возможности заново.
Ручное исправление CONFIG монитора не применяется.

Сохранённый STATUS `140407` соседнего модуля до RESET сам по себе не
означает, что служба всё ещё активна. Его конфигурация сохранена, а живое
состояние восстанавливается холодной инициализацией.

## Дополнительная RTL-проверка

Полный стенд CP67b использует SPI FRAM/SD/UART, сохранённые байты внешней
FRAM и штатные команды UJMOD. CPU-состояние не задаётся. Проверяются
CONFIG по динамическому указателю RMON `@54 + 300`, таблица всех восьми
модулей, исходный FIS-обработчик, адаптер и независимая работа ODT.
Вход в ODT без FPP проверяет вывод регистров и сообщение
`?FP11 DEBUG STATE UNAVAILABLE`; возврат в RT-11 ожидается по завершению
HALT-службы перед посылкой следующей команды.

Итог: **206 checks / 582937544 clocks / 2107 UART bytes, PASS**.
RT-11 CONFIG проходит `124141 → 124041 → 124141`: меняется бит `100`
наличия FPP. Без FPP обе FIS-сборки при семи командах ошибок/восстановления
исполняют **0 FPP opcodes / 0 HALT FPP entries**. После восстановления
FPP у B81FIJ зарегистрированы **4 / 4**: монитор штатно выполняет STST
при четырёх FIS-исключениях, а адаптер убирает дополнительные слова стека.
Все 32 слова таблицы сверяются после каждого изменения и cold boot.

Ранний запуск стенда отправлял следующую команду слишком рано после ODT
CONTINUE и потерял UART-символ. В окончательном стенде используется
завершение HALT-службы; повторный полный проход успешен. Это исправление
синхронизации теста, изменений в RTL процессора или ODT не было.

## Ресурсы и воспроизведение

FPGA прежняя: **1244 LUT / 381 FF / 7 EBR**, прирост от проверки — ноль.
OFF прекращает автоматическую активацию FPP, но не освобождает LUT или
размещение FRAM: это программный модуль, а OFF сохраняет его регистрацию.

Аппаратные фазы: `disable`, `fis-only`, `restore`, `combined`.
`fis-only` и `combined` сначала ждут свежий аппаратный RESET; сценарий
не имитирует его посылкой команды RT-11. Для всех последующих фаз передать
`--baseline <01-disable/session.json>` от первого этапа. Каждая фаза требует
новый `--out`; выбранный UART-reader восстанавливается даже при ошибке.

Локальный RTL-прогон после воспроизведения CP81:

```sh
python3 uJ11-fpga/tools/run_basic_modules_cp82.py \
  --out uJ11-fpga/build/cp82-modules/new-run
```

Архив [tb/reports/cp82-modules](../tb/reports/cp82-modules/) содержит
UART-фазы, исходную/конечную таблицы, frozen source и read-only SD image.
Для отдельного повтора распаковать `rtl/source.tgz` в новый каталог,
распаковать `rtl/test.dsk.gz` туда в `build/cp82-modules/rtl-c/test.dsk`,
создать `build/cp82-replay`. Массивы аргументов `compile` и `run` из
`rtl/replay.json` выполняются из корня распакованного дерева. Отдельный
lint распакованного архива прошёл; он не подменяет основной RTL-прогон.

Проверка сохранённых свидетельств без обращения к плате:

```sh
python3 uJ11-fpga/tools/verify_modules_cp82.py
```
