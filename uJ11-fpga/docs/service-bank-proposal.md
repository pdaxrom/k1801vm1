# Предложение: служебный банк FRAM без MMU

2026-09-12. Статус: исследование и предложение по запросу пользователя.
RTL и установленная CP56a не изменены; стоимость нового варианта ещё не измерена.

Уточнение после подробного чтения ВМ2: [CPC/CPSW, SEL, MFUS/MTUS и START/STEP](vm2-halt-reference.md).
ВМ2 не сохраняет все R0–R7 микрокодом и не пишет HALT-frame в стек.
Первым вариантом для оценки uJ11 теперь считать сохранение возвратных
PC/PSW с программным сохранением остальных регистров. Полный микрокодный
save ниже — альтернативный вариант, а не установленное требование.

## Назначение и совместимость

Использовать верхние 64 КиБ физической FRAM для монитора с интерфейсом ODT,
его стека/контекста и будущего программного эмулятора FP11. Код служб — обычные
PDP-11 инструкции в FRAM. Микрокод отвечает за вход/выход и доступ между банками.
FIS остаётся в существующем микрокоде.

Это расширение uJ11, вдохновлённое ВМ2. Оно не является стандартным HALT
пространством J-11 и не реализует MMU. У DEC J-11 консольный ODT выполняется
микрокодом (§9 и приложение 4 в [J-11 Programmer's Reference](../../doc/J-11_Programmers_Reference_Jan82.pdf));
вход предусмотрен по HALT, внешнему HALT и выбранному режиму power-up.
См. также [DCJ11 User's Guide, §2.5.2 и глава 5](https://www.bitsavers.org/pdf/dec/pdp11/1173/EK-DCJ11-UG-PRE_J11ug_Oct83.pdf).

[Локальное исследование КМ1801ВМ2](../../doc/KM1801VM2.pdf) описывает HALT/USER,
SEL, CPC/CPSW и MFUS/MTUS/START: именно доступ к другой памяти и восстановление
контекста делают системный банк полезным для монитора/эмулятора. Документ
является авторской компиляцией и исследованием УКНЦ, а не руководством DEC.
В нашем [тесте эмулятора ВМ2](../../lsi11/tests/test_vm2_banking.c) проверены
изоляция двух банков и общая I/O page. Эти тесты не доказывают готовность uJ11.

Бит служебного режима следует держать отдельно от архитектурного PSW J-11.
Нельзя присвоить битам CM/PM/RS или скопировать H/U из PSW ВМ2 новое значение
и при этом объявлять его стандартным поведением J-11.

## Что уже имеется

- Физическая FRAM 128 КиБ; контроллер имеет вход `bank` и передаёт его
  в адресном байте SPI. В native bus CP56 этот вход постоянно равен нулю.
- Существующие FRAM tests покрывают оба банка, но вход/возврат служебного
  режима и его взаимодействие с CPU/периферией ещё отсутствуют.
- CP56 сохраняет sequential READ только для `bank=0`: условие `retain`
  содержит `!bank`. Для первого опыта верхний банк можно читать обычными
  транзакциями. Ускорение верхнего банка потребует bank tag или закрытия CS
  на каждом переходе; одинаковые младшие адреса разных банков не являются hit.
- Текущий `HALT_ENTRY` пишет PC/PSW в стек гостя и читает вектор 4. Для
  монитора, который должен работать при испорченном SP, этот путь недостаточен.
- Все FP11 opcodes сейчас идут в reserved-instruction path. Готового полного
  PDP-11 firmware эмулятора FP11 в CP30 нет: там было только управляющее
  подмножество в микрокоде. Его resource cost нельзя переносить на новый способ.

Точные исходники установленного варианта: `synth/reports/cp56a/source.tgz`;
его FRAM генерируется профилем `--spi-cp56`, а не берётся из default RTL.

## Предлагаемая организация

| Доступ | Физическая память / назначение |
|---|---|
| Обычная программа | Нижний банк FRAM, прежняя CPU I/O page |
| Служебный код, данные, стек | Верхний банк FRAM, та же CPU I/O page |
| Служебный доступ к памяти программы | Нижний банк с явно заданной семантикой CPU memory/I/O |
| Физический доступ монитора/загрузчика | Явный банк и адрес, с обходом I/O decode для RAM |
| Текущий RK DMA | Прежний нижний банк независимо от служебного режима CPU |

Для RAM старший физический бит имеет смысл `{service_bank, address[15:0]}`.
Это выбор одного из двух фиксированных банков без PAR/PDR, translation,
отдельных I/D spaces или большого dual-read RF. Однако общего CSR,
произвольно меняющего bank в середине исполнения, недостаточно: следующая
выборка и стек должны переключаться согласованно с сохранением PC/PSW.

**64 КиБ — размер банка, а не объём одновременно доступной CPU RAM.**
При сохранённой I/O page `160000..177777` (восьмерично) прямо видны 56 КиБ RAM.
Для использования физических верхних 8 КиБ каждого банка нужен явный доступ
с обходом CPU I/O decode. Обычные обращения к устройствам при этом сохраняют
их адреса и побочные эффекты. Такой обход уже есть для части RK DMA, но его
нельзя без проверки распространять на монитор и произвольные CPU operands.

Нормальное ПО не получает линейные 128 КиБ и возможности RT-11XM. Оно
продолжает работать в прежнем пространстве; служебные программы не отнимают
его RAM. Полная совместимость MMU/processor modes J-11 этим не добавляется.

## Вход, работа, возврат

1. На границе инструкции закрыть незавершённый FRAM read stream и запретить
   принятие новых IRQ/trace на время сохранения. Зафиксировать причину входа.
2. По образцу ВМ2 сохранить возвратные PC/PSW, не используя стек программы;
   выбрать служебный банк и точку входа. Место копий — отдельные регистры
   или T-слова RF — выбрать по microcode budget и synthesis. R0–R6 остаются
   общими. Альтернатива для сравнения: полный микрокодный save R0–R7/PSW
   в фиксированный блок верхнего банка до запуска firmware.
3. При первом варианте firmware сохраняет нужные R0–R6 и старый SP прямыми
   обращениями к служебной памяти, затем устанавливает свой стек.
   Возвратные PC/PSW должны оставаться доступными и не перезаписываться.
   Необходим контролируемый read/write другого банка без изменения банка
   instruction fetch. Сначала оценить аналоги MFUS/MTUS с фиксированными
   R0/R5. Способ кодирования — отдельный малый эксперимент; не менять
   MFPI/MTPI или reserved opcodes гостя молча.
4. Восстановить контекст и атомарно вернуть банк/PC/PSW. У HALT продолжение
   идёт после HALT; у эмуляции — после всей FP-инструкции и её extension words.
   Изменённые эмулятором EA-регистры и требуемые flags должны попасть в контекст.

Первый режим допускает единственный служебный контекст. Вложенный вход,
fault при сохранении/возврате, трассировка и pending IRQ должны иметь явный
контракт. В частности, нынешний unmasked RK firmware assist нельзя оставить
способным перезаписать служебный контекст; простого IPL7 недостаточно.
`RESET` инструкции, power reset и возврат из монитора должны различаться.

Минимальный EBR bootstrap сохраняется: до входа в FRAM firmware нужно
проверить заголовок/версию/контрольную сумму и иметь путь восстановления.
FRAM энергонезависима, поэтому исправный образ не требуется перечитывать
с SD при каждом запуске. Формат и способ первоначальной загрузки — часть
отдельного loader milestone; образ RT-11 на SD автоматически не изменяется.

## FP11 поверх служебного банка

После работающего ODT можно направлять поддерживаемые FP opcodes во вход
эмулятора до обычного reserved trap. Другие reserved opcodes сохраняют trap
по `000010`; реальные FP arithmetic exceptions требуют своей семантики,
включая вектор `000244`. Само размещение кода в FRAM ещё не реализует FP11.

AC0–AC5, FPS/FEC/FEA, рабочие данные и арифметика находятся в верхнем банке.
Не нужны hardware multiplier/divider, расширенный RF или отдельный EBR для
FP state по предложенной схеме. Плата оплачивает код временем исполнения
PDP-11 инструкций и SPI cycles. Размер полного эмулятора и скорость нужно
измерить после сборки; обещать их сейчас нельзя.

Проверки должны охватить addressing modes, R6/R7 increments, immediate и
PC-relative operands, F/D/I/L, rounding/chopping, flags, memory faults,
exceptions и trace/IRQ после завершения инструкции. Существующий C-код
`core/pdp11_fp.c` пригоден как дополнительный эталон, но не как уже готовый
бинарник firmware для PDP-11 и не как замена спецификации FP11-A.

## Первый synthesis checkpoint

На CP56a свободны 96 LUT, 45 slices, 1 EBR и 70 фрагментированных слов
микрокода. Это пределы текущего полного board, не оценка цены service bank.
Один bank FF дёшев; decoder, вход/возврат, межбанковый доступ и arbitration
тоже потребуют ресурсов. Целевой прирост EBR — ноль, фактический fit неизвестен.

Сначала отдельный профиль поверх frozen CP56a: два банка, минимальный
ENTER/RETURN, сохранение контекста и тестовая служебная программа, которая
меняет слово памяти гостя и возвращается. Затем полный HC1200 synthesis,
сравнение LUT/FF/EBR/Fmax/microstore и неизменности обычного CPI.
До этого checkpoint не писать большой ODT или FP11 emulator.

Нужны bank isolation/alias tests, word/byte/odd/address-end tests,
переключение при удержанном CS, reset/fault/IRQ/trace, испорченный гостевой SP,
сохранение контекста, I/O side effects и RK DMA с активным служебным банком.
После unit/CPU tests — cold RT-11FB + DIR и hardware test отдельного JED.
Далее ODT и только затем программный FP11.
