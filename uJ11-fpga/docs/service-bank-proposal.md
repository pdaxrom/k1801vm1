# Предложение: служебный банк FRAM без MMU

2026-09-12. Выбранное пользователем направление: механизм HALT ВМ2,
но вход эмуляции предназначен для FP11; FIS остаётся в микрокоде.
Полные ODT и FP11 загружаются **из работающей RT-11** в верхнюю FRAM.
Первый отдельный профиль реализован: [CP57e](service-bank-cp57.md),
1260 LUT / 342 FF / 6 EBR / 31,982 MHz. Default и установленная CP56a
не менялись. Ниже сохранён полный выбранный контракт; его незавершённые
части перечислены в CP57 и TODO.

Уточнение после подробного чтения ВМ2: [CPC/CPSW, SEL, MFUS/MTUS и START/STEP](vm2-halt-reference.md).
ВМ2 не сохраняет все R0–R7 микрокодом и не пишет HALT-frame в стек.
Для uJ11 выбран вариант с возвратными PC/PSW и программным сохранением
остальных регистров. Полный микрокодный save не входит в выбранный контракт.

## Выбранный контракт переноса

- Два пространства, сигнал выбора HALT-памяти, CPC/CPSW, системные векторы,
  RSEL, RCPC/RCPS, WCPC/WCPS, MFUS/MTUS, START/STEP — по механизму ВМ2.
  Семантика инструкций и их HALT-only алиасы берутся из документации;
  в обычном режиме они остаются reserved instructions.
- Контекст PC/PSW сохраняется без обращения к стеку гостя. R0–R6 общие,
  их сохранение и собственный стек — задача служебной PDP-11 программы.
- Вход `SEL010` используется для синхронной эмуляции FP11-инструкций,
  а не FIS. Это не внешнее IRQ: IPL программы не может запретить эмуляцию
  инструкции. FIS не читает конфигурацию эмулятора и не входит в HALT.
- Аналог SEL[7] сообщает об отсутствии FP11 firmware. При его отсутствии
  FP11 сохраняет текущий путь unsupported/reserved instruction; остальные
  reserved integer opcodes также сохраняют обычный trap `000010`.
  FP11 decode/validation, его собственные illegal-operation и arithmetic
  exceptions определяются отдельно по спецификации FP11, включая `000244`.
- Формат PSW и IPL J-11 сохраняются. Поэтому это перенос **механизма HALT**,
  а не всего PSW/interrupt controller ВМ2: служебный режим хранится отдельно,
  CPSW имеет 16 бит. Представление сохранённого режима, управление замораживанием
  копий и его связь с START/STEP нужно явно определить в microcode/firmware ABI;
  9-битный PSW ВМ2 побитно не подставлять вместо J-11 PSW.
- Системный vector base и I/O mapping задаёт обвязка uJ11. Не переносить
  карту конкретной УКНЦ или режимы MMU/памяти других процессоров.
- Полные ODT и FP11 — отдельные файлы на диске RT-11, устанавливаемые
  программой под RT-11. Они не включаются в FPGA JED, EBR ROM или bootstrap
  с собственным чтением файловой системы. Существующий bootstrap загружает ОС.

Первый gate проверяет только механизм и тестовый FP11 handler, затем
синтезируется полный board. Полный ODT и FP11 firmware следуют после fit.

## Назначение и совместимость

Использовать верхние 64 КиБ физической FRAM для монитора с интерфейсом ODT,
его стека/контекста и будущего программного эмулятора FP11. Код служб — обычные
PDP-11 инструкции в FRAM. Микрокод отвечает за вход/выход и доступ между банками.
FIS остаётся в существующем микрокоде.

Это расширение uJ11, вдохновлённое ВМ2. Оно не является стандартным HALT
пространством J-11 и не реализует MMU. У DEC J-11 консольный ODT выполняется
микрокодом (§9 и приложение 4 в [J-11 Programmer's Reference](../../doc/J-11_Programmers_Reference_Jan82.pdf));
вход предусмотрен по HALT, внешнему HALT и выбранному режиму power-up.
См. также [DCJ11 User's Guide, §2.5.2 и глава 5](https://www.bitsavers.org/pdf/dec/pdp11/1173/EK-DCJ11-UG-PRE_J11ug_Oct83.pdf).

[Локальное исследование КМ1801ВМ2](../../doc/KM1801VM2.pdf) описывает HALT/USER,
SEL, CPC/CPSW и MFUS/MTUS/START: именно доступ к другой памяти и восстановление
контекста делают системный банк полезным для монитора/эмулятора. Документ
является авторской компиляцией и исследованием УКНЦ, а не руководством DEC.
В нашем [тесте эмулятора ВМ2](../../lsi11/tests/test_vm2_banking.c) проверены
изоляция двух банков и общая I/O page. Эти тесты не доказывают готовность uJ11.

Бит служебного режима следует держать отдельно от архитектурного PSW J-11.
Нельзя присвоить битам CM/PM/RS или скопировать H/U из PSW ВМ2 новое значение
и при этом объявлять его стандартным поведением J-11.

## Что уже имеется

- Физическая FRAM 128 КиБ; контроллер имеет вход `bank` и передаёт его
  в адресном байте SPI. В native bus CP56 этот вход постоянно равен нулю.
- Существующие FRAM tests покрывают оба банка, но вход/возврат служебного
  режима и его взаимодействие с CPU/периферией ещё отсутствуют.
- CP56 сохраняет sequential READ только для `bank=0`: условие `retain`
  содержит `!bank`. Для первого опыта верхний банк можно читать обычными
  транзакциями. Ускорение верхнего банка потребует bank tag или закрытия CS
  на каждом переходе; одинаковые младшие адреса разных банков не являются hit.
- Текущий `HALT_ENTRY` пишет PC/PSW в стек гостя и читает вектор 4. Для
  монитора, который должен работать при испорченном SP, этот путь недостаточен.
- Все FP11 opcodes сейчас идут в reserved-instruction path. Готового полного
  PDP-11 firmware эмулятора FP11 в CP30 нет: там было только управляющее
  подмножество в микрокоде. Его resource cost нельзя переносить на новый способ.

Точные исходники установленного варианта: `synth/reports/cp56a/source.tgz`;
его FRAM генерируется профилем `--spi-cp56`, а не берётся из default RTL.

## Предлагаемая организация

| Доступ | Физическая память / назначение |
|---|---|
| Обычная программа | Нижний банк FRAM, прежняя CPU I/O page |
| Служебный код, данные, стек | Верхний банк FRAM, та же CPU I/O page |
| Служебный доступ к памяти программы | Нижний банк с явно заданной семантикой CPU memory/I/O |
| Физический доступ монитора/загрузчика | Явный банк и адрес, с обходом I/O decode для RAM |
| Текущий RK DMA | Прежний нижний банк независимо от служебного режима CPU |

Для RAM старший физический бит имеет смысл `{service_bank, address[15:0]}`.
Это выбор одного из двух фиксированных банков без PAR/PDR, translation,
отдельных I/D spaces или большого dual-read RF. Однако общего CSR,
произвольно меняющего bank в середине исполнения, недостаточно: следующая
выборка и стек должны переключаться согласованно с сохранением PC/PSW.

**64 КиБ — размер банка, а не объём одновременно доступной CPU RAM.**
При сохранённой I/O page `160000..177777` (восьмерично) прямо видны 56 КиБ RAM.
Для использования физических верхних 8 КиБ каждого банка нужен явный доступ
с обходом CPU I/O decode. Обычные обращения к устройствам при этом сохраняют
их адреса и побочные эффекты. Такой обход уже есть для части RK DMA, но его
нельзя без проверки распространять на монитор и произвольные CPU operands.

Нормальное ПО не получает линейные 128 КиБ и возможности RT-11XM. Оно
продолжает работать в прежнем пространстве; служебные программы не отнимают
его RAM. Полная совместимость MMU/processor modes J-11 этим не добавляется.

## Вход, работа, возврат

1. На границе инструкции закрыть незавершённый FRAM read stream и запретить
   принятие новых IRQ/trace на время сохранения. Зафиксировать причину входа.
2. По образцу ВМ2 сохранить возвратные PC/PSW, не используя стек программы;
   выбрать служебный банк и точку входа. Место копий — отдельные регистры
   или T-слова RF — выбрать по microcode budget и synthesis. R0–R6 остаются
   общими.
3. Firmware сохраняет нужные R0–R6 и старый SP прямыми
   обращениями к служебной памяти, затем устанавливает свой стек.
   Возвратные PC/PSW должны оставаться доступными и не перезаписываться.
   Необходим контролируемый read/write другого банка без изменения банка
   instruction fetch. Сначала оценить аналоги MFUS/MTUS с фиксированными
   R0/R5. Способ кодирования — отдельный малый эксперимент; не менять
   MFPI/MTPI или reserved opcodes гостя молча.
4. Восстановить контекст и атомарно вернуть банк/PC/PSW. У HALT продолжение
   идёт после HALT; у эмуляции — после всей FP-инструкции и её extension words.
   Изменённые эмулятором EA-регистры и требуемые flags должны попасть в контекст.

Первый режим допускает единственный служебный контекст. Вложенный вход,
fault при сохранении/возврате, трассировка и pending IRQ должны иметь явный
контракт. В частности, нынешний unmasked RK firmware assist нельзя оставить
способным перезаписать служебный контекст; простого IPL7 недостаточно.
`RESET` инструкции, power reset и возврат из монитора должны различаться.

## Загрузка служб из RT-11

По прямому требованию пользователя загрузка полного ODT и полного FP11
выполняется из RT-11. Сначала штатно загружается RT-11 в нижний банк,
затем запускается обычная программа-загрузчик `.SAV`. Планируемые файлы:
`UJLOAD.SAV`, `ODT.BIN`, `FP11.BIN` (ещё не реализованы; синтаксис запуска
будет задан вместе с CLI). ODT и FP11 допускают независимую установку.

Последовательность загрузчика:

1. Прочитать заголовок файла средствами RT-11, проверить тип модуля,
   версию ABI, длину, выравнивание/диапазон адресов и точки входа.
2. Снять флаг готовности целевого модуля **до** перезаписи его области.
   Файловые операции и обработка ошибок диска выполняются только в RT-11.
3. Читать файл порциями в небольшой буфер нижней памяти и переносить
   в выделенную область верхнего банка через минимальный установочный вызов.
   Сам загрузчик остаётся в нижнем банке, с рабочими стеком и прерываниями RT-11.
4. Прочитать записанные данные обратно и программно проверить контрольную
   сумму. Проверить отсутствие пересечения с другим модулем, векторами,
   сохранённым контекстом и служебным стеком. CRC hardware не требуется.
5. Инициализировать данные модуля (включая FP state при новой установке),
   опубликовать векторы и только последним действием выставить его ready.
   При ошибке или прерывании загрузки модуль остаётся выключенным.

Такой loader требует **небольшого расширения относительно ВМ2**: в USER
его MFUS/MTUS запрещены и дают доступ только из HALT в USER. Они сами по
себе не позволяют RT-11 впервые заполнить пустой HALT-банк. Поэтому первый
resource gate должен включать установочный доступ к верхней FRAM, который
работает без уже загруженных ODT/FP11. Первый кандидат — микрокодный вызов
копирования/проверочного чтения с фиксированными регистрами; opcode, ABI,
границы доступа и максимальную задержку IRQ определить до RTL. HALT-only
команды ВМ2 не становятся доступными обычному коду из-за наличия загрузчика.
Установочный интерфейс является явным расширением uJ11, не механизмом защиты.

На cold reset ready-флаги сбрасываются: старые байты в энергонезависимой
FRAM не считаются автоматически установленными службами. RT-11 loader
загружает и включает их; его можно будет запускать из startup command file.
Обычная PDP-11 команда RESET периферии сама по себе не должна отменять
установленные службы; её точный контракт проверяется отдельно.

До установки ODT сохраняется исходный HALT/restart path CP56; до установки
FP11 — текущий reserved trap. Начальная загрузка RT-11 и сам UJLOAD не
зависят от FP11, используют integer ISA. Поэтому повреждённый или отсутствующий
служебный файл не должен мешать загрузке ОС и повторному запуску UJLOAD.
Обновление ODT/FP11 после реализации не требует новой прошивки FPGA при
совместимом ABI. Отдельная первая прошивка FPGA с механизмом банков нужна.

Текущий EBR bootstrap продолжает только свою прежнюю работу. Структура
SD-карты/образ RT-11 на данном этапе не изменялись. В тестах обязательны
отсутствующий/обрезанный файл, несовместимый ABI, checksum mismatch,
прерванная загрузка, повторная установка и сохранность гостевой памяти/RK DMA.

## Два интерфейса ODT: UART и настоящий пульт

По предложению пользователя ODT должен иметь и UART-интерфейс, и отдельный
интерфейс для HDSP/клавиатуры. Общими остаются сохранённый контекст, чтение/
запись памяти и регистров, проверка адресов, START/STEP и возврат в программу.
Панельный интерфейс работает с тем же состоянием, без отдельной копии CPU.
Код обоих интерфейсов загружается из RT-11 в служебную FRAM вместе с ODT.

Уже имеющаяся панель: два HCMS-3917, суммарно 16 символов, матрица 20 клавиш
и RGB LED. База переносимого программного драйвера —
`demos/rt11/panel/PNLDRV.MAC`, CSR `166000/166001`. Существующие исходники
демонстраций и их manifests сохраняются; HALT-вариант драйвера делать отдельно.
Физическая раскладка по изображению пользователя — 0–F и
MEM/PREV/NEXT/ENTER, без отдельной ESC; [раскладка и управление](panel-keyboard.md).
Предусмотреть OCT по умолчанию и HEX, команды запуска/шага выбирать в меню.

План интерфейса: восьмеричный адрес и слово на одном экране (например,
`012340: 012345`), отдельные экраны R0–R7/PSW, редактирование по цифрам,
переход к соседнему слову/регистру, запуск, продолжение и шаг. RGB отображает
режим остановки/редактирования/ошибки; точные переходы экранов и цвета — следующий
этап UI, не новые аппаратные состояния процессора. Одновременно память и
контекст редактирует один интерфейс; переключение UART/панель должно быть явным.

После установки из RT-11 работа в HALT не должна требовать вызовов RT-11
или её IRQ. В частности, `PNWAIT` текущего demo опирается на 50-Гц счётчик
RT-11; для монитора нужны собственные polling/debounce и проверенные задержки.
Новый framebuffer или аппаратный scanner для самого интерфейса не нужны.

Клавиатура и HG используют общие pins, поэтому их владение согласуется
при входе/выходе; одновременно сканировать клавиши и обслуживать HG нельзя.
Кнопка запроса HALT во время работы гостя — отдельная задача: один только
код сканирования внутри уже остановленного монитора её не обеспечивает.
Не добавлять фоновый hardware scanner без отдельного resource gate.

## FP11 поверх служебного банка

Первый gate направляет FP opcodes в тестовый служебный handler. Полный
эмулятор добавляется после рабочего ODT. Другие reserved integer opcodes сохраняют trap
по `000010`; реальные FP arithmetic exceptions требуют своей семантики,
включая вектор `000244`. Само размещение кода в FRAM ещё не реализует FP11.

AC0–AC5, FPS/FEC/FEA, рабочие данные и арифметика находятся в верхнем банке.
Не нужны hardware multiplier/divider, расширенный RF или отдельный EBR для
FP state по предложенной схеме. Плата оплачивает код временем исполнения
PDP-11 инструкций и SPI cycles. Размер полного эмулятора и скорость нужно
измерить после сборки; обещать их сейчас нельзя.

Проверки должны охватить addressing modes, R6/R7 increments, immediate и
PC-relative operands, F/D/I/L, rounding/chopping, flags, memory faults,
exceptions и trace/IRQ после завершения инструкции. Существующий C-код
`core/pdp11_fp.c` пригоден как дополнительный эталон, но не как уже готовый
бинарник firmware для PDP-11 и не как замена спецификации FP11-A.

## Первый synthesis checkpoint

На CP56a свободны 96 LUT, 45 slices, 1 EBR и 70 фрагментированных слов
микрокода. Это пределы текущего полного board, не оценка цены service bank.
Один bank FF дёшев; decoder, вход/возврат, межбанковый доступ и arbitration
тоже потребуют ресурсов. Целевой прирост EBR — ноль, фактический fit неизвестен.

Сначала отдельный профиль поверх frozen CP56a: два банка, минимальный
ENTER/RETURN, сохранение контекста, установочный доступ из обычного режима
без готового HALT firmware и тестовая служебная программа, которая
меняет слово памяти гостя и возвращается. Затем полный HC1200 synthesis,
сравнение LUT/FF/EBR/Fmax/microstore и неизменности обычного CPI.
До этого checkpoint не писать большой ODT или FP11 emulator.

Нужны bank isolation/alias tests, word/byte/odd/address-end tests,
переключение при удержанном CS, reset/fault/IRQ/trace, испорченный гостевой SP,
сохранение контекста, I/O side effects и RK DMA с активным служебным банком.
После unit/CPU tests — cold RT-11FB + DIR, загрузка тестового handler
программой RT-11 и hardware test отдельного JED. Далее загружаемый ODT
и затем полный программный FP11 с тем же путём установки из RT-11.
