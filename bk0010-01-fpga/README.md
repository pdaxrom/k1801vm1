# БК0010-01 FPGA

БК0010-01 для **Z-pdaXrom-TV hardware-lcd**: ВМ1А из cpu11,
32 КиБ RAM, MONIT10/BASIC10 с SD, PS/2, композитный PAL, звук
и переключение частоты **3 → 6 → 12 → 24 → 3 МГц**.
Короткое нажатие кнопки меняет частоту; удержание около двух секунд
выполняет тёплый сброс. Индикатор показывает применённый режим:
`03`, `06`, `12`, `24`. Магнитофон пока не подключён.

RTL и двухэтапный загрузчик реализованы. Проверки запуска оригинального
ПЗУ, BASIC, SD/FAT16, PS/2, панели, CDC и видеовывода находятся в `tests/`.
Предыдущий полный SoC-тест прошёл: cold/warm boot через физические модели SRAM/SD,
PS/2 `PRINT 2+2`, live switch всех четырёх частот, PAL без underrun;
ROM и VRAM совпали с эталоном. Сводка — [research/implementation-checks.json](research/implementation-checks.json),
подробные отчёты — `build/results-*.json`.
Diamond 3.14 на прежнем Linux-стенде uJ11 выполнил Synthesis/MAP/PAR/TRACE:
все сигналы разведены, setup/hold без ошибок, CPU до 24 МГц.
Прошивка и отчёты — [releases/hardware-lcd-pal-20261005](releases/hardware-lcd-pal-20261005/README.md).
Flash прошита и проверена на плате; SD/FAT16 загрузка и обе CRC-проверки SRAM
прошли, PAL вывел BASIC. Пользователь подтвердил PS/2 `PRINT 2+2`, индикатор,
все четыре режима частоты и длинный RESET. Аппаратные логи и наблюдения —
[research/hardware/20261005-pal](research/hardware/20261005-pal/README.md).
Уровни PAL и производительность относительно реальной БК пока не измерены.
Подробная архитектура и исходная проверка источников — в [PLAN.md](PLAN.md).

## Сборка и проверки

Нужны Python 3, Icarus Verilog, Verilator с C++ toolchain и `microasm11`
из соседнего каталога. При другом расположении ассемблера задайте
`MICROASM11=/absolute/path/to/microasm11`.

```sh
cd bk0010-01-fpga
make build
make test
make test-boot
make test-soc
# Аппаратная ветвь RTL с официальной моделью DCCA из установленного Diamond:
make test-soc-diamond DCCA_MODEL=/absolute/path/to/Diamond/cae_library/simulation/verilog/machxo2/DCCA.v
```

- `make build`: `build/boot.bin`, `boot.hex`, `LOADERBK.BIN`, `BK0010.ROM`,
  `bk0010-sd.img`, листинги и `artifacts.json` с SHA-256.
- `make test`: кнопка/частоты/сегменты, асинхронная шина, физический PS/2,
  UART, четырёхсостоянийная SRAM, lint SoC, монохромный и цветной PAL через SRAM.
- `make test-boot`: MONIT/BASIC и `PRINT 2+2`, SDHC/SDSC-v1,
  фрагментированный файл, тёплый сброс и повреждения SD/SRAM.
  Заново запускает исходный C-эмулятор и сравнивает все 32 КиБ ПЗУ
  и 16 КиБ VRAM с эталоном. C-эталон отдельно: `make test-reference`.
- `make test-soc`: полный компьютер с реальными фазами CPU и частотами
  периферии, моделями физических SRAM/SD/PS/2, PAL, кнопкой и BASIC.
  Только длительности debounce кнопки ускорены для моделирования.
- `make test-plm`: сравнение исходной и преобразованной PLM ВМ1А/ВМ1Г
  на 44 768 парах входов. Icarus выполняет его заметно дольше остальных
  локальных проверок. `make test-all` выполняет fast, boot и soc.

Каждая группа пишет `build/results-<group>.json` и отдельные логи команд.
Ненулевой exit code, `$fatal` и несовпадение эталонных байтов считаются ошибкой.
Отчёты содержат хеши исходников. Видеопамять эталона получена из исходного
C-эмулятора `../bk0010-01`, без изменений его файлов; детали и изображения
сохранены в `research/`.

## SD и запуск

`build/bk0010-sd.img` — обычный файл размером 17 МиБ: MBR, первая
FAT16-разметка с началом LBA 2048 и объёмом 16 МиБ. В её корне находятся:

```text
LOADERBK.BIN — второй этап, native ВМ1, адрес 020000
BK0010.ROM  — заголовок 512 байт + MONIT10 8192 + BASIC10 24576
```

EBR содержит только небольшой первичный загрузчик. CPU сам инициализирует
SD, читает FAT16 и загружает `LOADERBK.BIN`. Второй этап проверяет заголовок,
CRC32 потока и CRC32 чтения SRAM, блокирует запись в ПЗУ и передаёт управление
MONIT по адресу `100000`. Схема перенесена из pyldin601-fpga;
дополнительного процессора загрузки нет.
Имя `LOADER.BIN` остаётся за Пълдином: оба загрузчика могут находиться
в корне одной карты, БК ищет только `LOADERBK.BIN`.

После тёплого сброса ПЗУ и lock сохраняются: MONIT стартует из SRAM,
SD повторно не читается. При выключении питания или потере PLL lock
происходит новая холодная загрузка. Повреждённый образ оставляет bootstrap
активным и выводит код ошибки на PAL/UART.

Первичная версия читает **первый MBR-раздел типа 06/0E**, FAT16 с 512-байтными
секторами, 1–128 секторами на кластер, одним/двумя FAT, до 512 записей root
и максимум 65 535 секторами в томе. Имена — uppercase 8.3; загрузочные файлы
лежат в корне. Цепочки могут быть фрагментированы. FAT32, exFAT, superfloppy
и длинные имена не поддерживаются. Для полного перечня регистров и ошибок
см. [docs/boot.md](docs/boot.md).

Скрипт `tools/make_sd.py --out <новый-файл.img>` отдельно создаёт образ
без перезаписи существующего файла. `make build` обновляет только собственные
артефакты в `build/`. Физическую SD-карту эти команды не записывают.

## Клавиатура, видео и диагностика

Используется PS/2 Scan Set 2. Латинские буквы и символы соответствуют US-layout;
Shift/Caps меняют регистр, Shift — пунктуацию. Enter передаёт `012`, Backspace —
`030`, стрелки — коды БК. Esc — STOP; Alt выбирает прерывание `274` вместо `60`.
F10/F11 передают РУС/ЛАТ (`016`/`017`). Ctrl-G/M/P/R/T/U соответствуют
shortcut-кодам эталонного эмулятора. Цифровой блок передаёт цифры;
переключение NumLock и управление светодиодами клавиатуры пока отсутствуют.
Нажатия модификаторов отдельно не запускают повтор предыдущего символа.

PAL использует 64 МГц, 625 строк/50 полей и два строковых буфера EBR.
По умолчанию отображается 512×256, LSB-first, чёрный/белый.
Активное окно: такты 718…3917, строки 32…287 и 345…600.
Кадр сдвинут на 8 точек влево и 4 строки вниз; пользователь подтвердил,
что строка загрузчика и правые символы BASIC полностью помещаются на LCD.
Параметр `COLOR=1` в SoC включает 256×256 и пары битов
`00` чёрный / `01` синий / `10` зелёный / `11` красный.
Регистр `177664` управляет прокруткой; изменения применяются на границе поля.
Режим РП следует фактическому поведению C-эмулятора: 64 строки из `070000`
повторяются по высоте. SRAM-арбитр чередует CPU и видеодоступ при конкуренции.

UART TX: **115200 8N1**, сообщения `B:01`…`B:07`, `B:FF` или `E:xx`, CR/LF.
RX не используется. RGB LED: инициализация SRAM, lock ПЗУ, ошибка bootstrap
или пропуск видеостроки. Звук — системный порт БК, bit 6, на оба выхода audio.
Системный порт и таймер принадлежат встроенной периферии ядра ВМ1А.
Таймер работает от CPU clock и ускоряется вместе с процессором.

## Diamond и плата

```sh
make diamond
# При иной маркировке или повторной подготовке используйте новый каталог:
python3 tools/diamond_project.py --device LCMXO2-7000HC-4TG144C --out build/diamond-next
```

Пакет `build/diamond/` самодостаточен: относительные пути LDF, исходники,
boot.hex, объединённый `clock.lpf`, FDC, strategy, `inputs.json`, проверяющий
скрипт и `build.tcl`. Скопируйте его на Linux и из каталога пакета выполните:

```sh
env LD_PRELOAD=/lib/x86_64-linux-gnu/libstdc++.so.6 \
    ~/.local/lscc/diamond/3.14/bin/lin64/diamondc build.tcl
python3 tools/diamond_report.py export .
```

`build.tcl` выполняет Synthesis/Translate/MAP/PAR/TRACE, отдельно подтверждает
обе CPU-фазы и автоматически проверяет все явные ограничения. Экспорт проверяет
хеши исходников и NCD, обе контрольные суммы JEDEC и число fuse bits.
Результат — `impl1/bk0010_impl1.jed` и `result.json`; плату скрипты не программируют.
Стенд uJ11: `sash@192.168.1.108`, Diamond — путь выше.

По умолчанию выбран **LCMXO2-7000HC-4TG144I** из схемы hardware-lcd.
uJ11 собирался для `…C`; перед окончательной сборкой требуется фактическая
маркировка FPGA. Кварц предполагается **12 МГц** по рабочему проекту uJ11.
Новая main PLL даёт 24/48 МГц, отдельная PAL PLL — 64 МГц.
CPU p/n используют одну сеть DCCA: отрицательный фронт реализуют clock polarity
mux регистров и EBR. Имена тактов сохранены для LPF.
Документация примитива — [Lattice sysCLOCK](https://www.latticesemi.com/view_document?document_id=39080).

TRACE подтвердил clock/I/O/MAXDELAY пути, половину периода CPU, setup/hold
и сохранение synchronizer-стадий. Первая стадия CDC исключена; удерживаемые
payloads имеют явные MAXDELAY. Подробнее — [docs/timing.md](docs/timing.md).
Официальные EBR-модели с параметрами итогового EDIF проверили все 4096 слов
bootstrap и 64 слова двухтактового строкового буфера, включая сохранение при GSR.
Повторить эту проверку после сборки можно из корня проекта:

```sh
python3 tools/test_mapped_ebr.py /absolute/path/to/impl1/bk0010_impl1.edi \
    /absolute/path/to/Diamond/cae_library/simulation/verilog/machxo2
```

Это проверка примитивов памяти; полная post-route SDF-симуляция не выполнялась.
Калибровка производительности режима 3 МГц относительно реальной БК
и измерение физических уровней PAL остаются следующими этапами.
