# План реализации БК0010-01 для FPGA hardware-lcd

Проверка источников выполнена 4 октября 2026 года. Цель — автономный
БК0010-01 на Z-pdaXrom-TV hardware-lcd с ядром ВМ1А из cpu11,
исходными MONIT10/BASIC10, клавиатурой PS/2 и композитным PAL.
ПЗУ храним на SD и загружаем двухэтапным программным bootstrap,
как в pyldin601-fpga. Частоту CPU переключаем короткой кнопкой,
текущую частоту в МГц показываем на двухразрядном индикаторе платы.
Загрузку с магнитофона пока не реализуем.

Этот документ фиксирует архитектуру и порядок реализации. Top-level, native
SD-bootstrap и локальные тесты уже реализованы; текущее использование описано
в [README.md](README.md). JED прошёл MAP/PAR/TRACE на Linux-стенде uJ11;
артефакты — [releases/hardware-lcd-pal-20261005](releases/hardware-lcd-pal-20261005/README.md).
Результаты предварительных проверок сохранены в [research/checks.json](research/checks.json).

## Состав первой рабочей версии

В первую версию входят ВМ1А, 32 КиБ RAM, оригинальные MONIT10 и BASIC10,
таймер ВМ1, регистры клавиатуры/прокрутки/системного порта, PS/2,
монохромное изображение 512×256, PAL и однобитный звук,
переключение частоты кнопкой и её индикация в МГц.
Цветной вывод 256×256 на четыре цвета добавляем после сверки монохромного
кадра; это второй способ интерпретации той же экранной памяти.

SD используется для bootstrap и хранения ROM. Дисковый контроллер,
расширенная память БК0011, SERV, терминал VT и мышь в эту реализацию
не входят. Магнитофонный вход имеет постоянное неактивное значение;
его выходные биты сохраняются в системном порту, бит звука работает.
Команды ROM для магнитофона остаются исходными, но обмен лентой не обслуживается.

## Плата и ограничения ресурсов

В схеме установлен LCMXO2-7000HC-4TG144I, SRAM IS61WV102416BLL
1M×16, то есть 2 МиБ. Для окончательного device в Diamond нужно
сверить маркировку экземпляра: проект uJ11 использует вариант C,
а схема и проект Пълдина — I.
Внешние 12 МГц подтверждены конфигурациями существующих проектов;
сама схема не содержит значения частоты Q1.

| Сигнал | Физический вывод FPGA |
|---|---|
| clock / reset button | 3 / 38, кнопка активна нулём |
| PS/2 CLOCK / DATA | 2 / 138 |
| PAL DAC bits 0…5 | 142, 143, 1, 141, 140, 139 |
| SD CS / SCK / MISO / MOSI | 40 / 44 / 45 / 71 |
| UART TX / RX со стороны FPGA | 132 / 133 |
| Audio R / L | 21 / 22 |

Остальные назначения SRAM берём из проверенного LPF uJ11 и сверяем
с CSV hardware-lcd. PS/2 питается от 3,3 В; CLOCK со стороны FPGA
управляется как 0/Z. Мышиная пара 4/5 отдельная. На SD доступен SPI,
сигналы обнаружения карты не подключены.

В FPGA 26 блоков EBR по 9 Кбит. MONIT10 занимает 8192 байта,
BASIC10 — 24576 байт: оба ROM целиком в EBR не помещаются.
Поэтому 32 КиБ штатных ROM размещаем во внешней SRAM, а в EBR
оставляем только первичный bootstrap, регистры ядра и видеобуферы.
Первичный bootstrap целимся разместить в пределах 8 КиБ, до 8 EBR;
фактический размер определяем после сборки MACRO-11.
Регистровая память ядра требует отдельной оценки на MachXO2,
строковый видеобуфер — примерно один EBR. Итоговые LUT/EBR/PLL
может подтвердить только MAP/PAR; оценки других семейств cpu11
не являются оценкой этого проекта.

## Ядро и шина

Выбираем `vm1/hdl/wbc/rtl`: `vm1_wb.v`, `vm1_plm.v`,
`vm1_tve.v`, `vm1_reg.v`. Параметр `VM1_CORE_MULG_VERSION=0`
выбирает ВМ1А. ВМ1Г с MUL и прерыванием таймера не включаем.
Асинхронный вариант org и Qbus-вариант syn для этого SoC не нужны.

У ядра три интерфейса: мастер памяти, slave собственных регистров
и подтверждение вектора прерывания. Диапазон 177700–177716 маршрутизируем
в slave ядра; входы `vm_reg14`/`vm_reg16` и выходы `vm_sel[2:1]`
связываем с портами БК. Таймер по 177706/177710/177712 уже есть в ядре.
Клавиатура подаёт VIRQ и вектор 060 либо 274 через интерфейс wbi.
СТОП подаём на радиальный вход `vm_irq[1]`, отдельно от reset.

Внешний адрес мастера байтовый, адрес SRAM словный: `address >> 1`.
Byte lanes соблюдаем для памяти и регистров, особенно при нечётной
байтовой записи. Встроенный slave не имеет отдельного входа byte select,
поэтому семантику его байтовых обращений проверяем на реальном ядре.
Побочные эффекты портов выполняем один раз на завершённую фазу обмена.
Проверяем RMW: CYC может сохраняться между чтением и записью,
а STB — сниматься и выставляться повторно.

`wbm_ios_o` устанавливается для адресов от 160000. У БК в этом диапазоне
ещё находится BASIC до 177577, поэтому один этот сигнал не может
выбирать всю периферию. Декодер следует карте БК и различает ROM
и реальные CSR по полному адресу. Неизвестный CSR и запрещённая запись
в ROM не получают ACK; отрабатывает собственный timeout ядра.
Добавлять фиктивный Wishbone ERR нельзя: такого входа у vm1_wb нет.

Для первого прототипа рассматриваем постоянный системный clock 24 МГц
для SRAM/PS/2/SPI/кнопки/индикатора и отдельный video clock 64 МГц.
CPU и его Wishbone-интерфейсы работают в отдельном домене с выбираемой
частотой. Между CPU и системной шиной нужен явный мост с согласованной
передачей запроса/ответа, byte lanes и RMW, без повторных побочных эффектов.
Частоты PAL, SRAM, SD, UART и времени debounce не меняются вместе с CPU.

Ядро использует положительную и отрицательную фазы `vm_clk_p/n`;
пути между фазами требуют проверки за полупериод в каждом режиме.
Для переключения проектируем делитель и разводку clock средствами MachXO2,
с generated-clock constraints и проверкой формы импульсов после трассировки.
Комбинационный mux тактовых сигналов не допускается. `vm_clk_slow`
компенсирует скорость запуска транзакций и не является общим clock enable
ядра; один делитель этого строба не выполняет требование смены частоты CPU.

Исходный режим — 3 МГц. Тактовая частота и скорость выполнения программ
различаются: совместимость этого режима с исходным БК калибруем по
инструкциям, таймеру и доступам к памяти. Для таймера отдельно фиксируем
политику `vm_clk_tve` и проверяем её при переходе между режимами.

## Кнопка частоты и двухразрядный индикатор

Используем кнопку `reset_n` на pin 38 и механизм `uj11_button`:
двухступенчатую синхронизацию, период выборки 20 мс и подтверждение
двумя одинаковыми выборками. Короткое нажатие выдаёт ровно одно событие
после подтверждённого отпускания. Удержание около 2 секунд выполняет
тёплый аппаратный reset; его отпускание не меняет частоту.
Контроллер кнопки и сканер индикатора сбрасываются только power-on,
поэтому удержание reset не останавливает debounce и индикацию.
СТОП остаётся клавишей Esc и радиальным прерыванием ВМ1.

Выбранный пользователем цикл: **3 → 6 → 12 → 24 → 3 МГц**.
Повышенные режимы допускаются в сборку только после успешных
MAP/PAR/TRACE и интеграционных тестов.
После конфигурации начинаем с 3 МГц; тёплый reset сохраняет выбранный режим.
Переключение работает при обычном исполнении, WAIT и во время bootstrap.
Оно не сбрасывает CPU, ROM-lock, память и устройства.

Событие кнопки создаёт запрос новой частоты. Применяем его после завершения
текущей передачи CPU на границе полного периода, сохраняя обе фазы,
минимальную ширину импульсов и все ожидающие IRQ. Таймаут незавершённой
передачи должен продолжать работать до её завершения. Регистр текущей
частоты обновляется после применения режима, а индикатор берёт его
согласованным кадром: оба разряда всегда относятся к одному значению.

Число на индикаторе — применённая тактовая частота CPU в десятичных МГц:
`03`, `06`, `12`, `24`. Это не измеритель MIPS.
Обе точки выключены. Во время длительного reset сохраняется число частоты;
сканер продолжает работать от постоянного системного clock.

Разводку берём из LPF uJ11 и сверенной таблицы hardware-lcd:

| Разряд | A | B | C | D | E | F | G | DP | Общий анод |
|---|---|---|---|---|---|---|---|---|---|
| Левый `seg_led_h` | 115 | 117 | 103 | 99 | 98 | 114 | 113 | 104 | 100 |
| Правый `seg_led_l` | 127 | 128 | 111 | 106 | 105 | 122 | 121 | 112 | 107 |

В каждом порту бит 8 — активный высокий анод, бит 7 — DP,
биты 6…0 — активные низкие G…A. Переносим посегментный сканер uJ11,
заменяя диагностические буквы таблицей цифр 0…9. Одновременно выбран
не более одного сегмента во всём индикаторе. Четыре фазы — гашение анодов,
установка катода, импульс анода, гашение. Обходим все 16 позиций,
включая выключенные DP; заполнение каждого сегмента остаётся 1/64.
При 24 МГц делитель 750 даёт 32 кГц фаз и 500 Гц полного кадра.
Изменение числа полностью видно не позднее двух кадров, около 4 мс.
Все 18 выводов получают `LVCMOS33`, `DRIVE=4`, `SLEWRATE=SLOW`.
На установленной плате uJ11 отсутствуют токоограничивающие резисторы:
переносим именно этот способ сканирования; DRIVE и заполнение не являются
ограничителями пикового тока, измерение остаётся частью проверки платы.

Тестируем дребезг, один шаг на короткое нажатие, переход последнего режима
к первому, удержание/отпускание reset и кнопку при power-on. Для каждой
цифры и смены числа восстанавливаем кадр по реальным выходам; проверяем
порядок разрядов, полярность, единственный сегмент, гашение и заполнение.
Смена частоты проверяется с активной SRAM/SD, byte/RMW, timeout, WAIT/IRQ
и непрерывным PAL: без потери транзакций, клавиш, IRQ и строк видео.

## Карта памяти после загрузки

Все адреса БК ниже восьмеричные; физические смещения SRAM указаны hex.

| Адрес БК | Назначение | Физическая SRAM |
|---|---|---|
| 000000–037777 | 16 КиБ RAM пользователя, стек и переменные | 0x0000–0x3fff |
| 040000–077777 | 16 КиБ экранной RAM, доступной CPU | 0x4000–0x7fff |
| 100000–117777 | MONIT10, 8 КиБ, защищённое чтение | 0x8000–0x9fff |
| 120000–177577 | BASIC10, кроме перекрытого окна CSR | 0xa000–0xff7f |
| 177600–177777 | CSR либо timeout, без чтения ROM под ними | — |

Файл BASIC10 имеет полные 24 КиБ. Последние 128 байт находятся под
окном регистров и не видны CPU. Загружаем и проверяем полный файл.
Монитор начинает работу по 100000, полученному из регистра 177716.

| CSR | Реализация |
|---|---|
| 177660 | Ready bit 7, запрет прерываний bit 6 |
| 177662 | Семибитный код клавиатуры, чтение снимает Ready |
| 177664 | Прокрутка в bits 7:0, полный/РП экран в bit 9; reset 001330 |
| 177700–177704 | Встроенные регистры ВМ1 |
| 177706–177712 | Встроенный таймер ВМ1 |
| 177714 | Параллельный порт БК через vm_reg14/vm_sel |
| 177716 | Стартовый адрес и системный порт через vm_reg16/vm_sel |

Пока нет физической периферии параллельного порта, его вход задаём
константой 177777, выход храним отдельно. Назначения на GPIO выбираются
отдельно при добавлении конкретного устройства.

## Загрузка ROM с SD по схеме pyldin601-fpga

В текущем Пълдине SD и FAT16 обслуживает основной MC6800 программно.
Первичный ROM размером 4 КиБ читает LOADER.BIN, а небольшой второй этап
пишет ROM через служебный порт, проверяет CRC потока и повторно читает
SRAM для проверки сохранённых данных. Lock сохраняется при warm reset.
Аппаратный FAT-reader из `audit/previous-prototype` не переносим.

Для БК алгоритмы переносим на MACRO-11 и исполняем тем же ВМ1А.
Берём за основу `boot_spi_registers.v` и `spi_byte_master.v` Пълдина,
а boot-порты адаптируем к 16-битной шине и карте БК.
Первичный bootstrap временно перекрывает 100000–117777.
Это позволяет сохранять штатный стартовый адрес ВМ1 100000.

Последовательность холодного запуска:

1. PLL/reset и безопасные состояния SRAM/SD, инициализация рабочей RAM.
   После готовности памяти ВМ1 запускается в первичном ROM.
2. Первичный ROM инициализирует SD в SPI, различает SDSC и SDHC,
   проверяет MBR/BPB и открывает LOADERBK.BIN в корне первого FAT16-раздела.
   Размер сектора 512 байт, имена 8.3, поддержана цепочка кластеров.
3. LOADERBK.BIN загружается в обычную RAM, предлагаемый адрес 020000.
   Адрес, предел размера, стек, секторный буфер и API первичного ROM
   фиксируем в отдельном ABI перед написанием ассемблера.
4. Второй этап открывает BK0010.ROM: заголовок 512 байт,
   затем MONIT10+BASIC10 в исходном порядке, payload ровно 32768 байт.
   Заголовок содержит magic/version, размер, базу 0x8000,
   стартовый адрес и CRC32. Поля формата и CRC заголовка фиксируем тестом.
5. После проверки заголовка payload записывается в SRAM 0x8000–0xffff
   через служебное окно с автоинкрементом. Каждая запись ждёт завершения
   SRAM и выполняется ровно один раз. Проверяется CRC32 потока.
6. Весь payload повторно читается из SRAM и проверяется CRC32.
   До успешной проверки штатные ROM недействительны и защищённый запуск запрещён.
7. Завершается SPI, включается ROM lock, снимается bootstrap overlay
   и выполняется переход к штатному MONIT10 по 100000.

Для handoff нужен короткий исполняемый из RAM trampoline, как в Пълдине:
overlay нельзя отключать, продолжая выбирать инструкции из заменяемого ROM.
Проверяем это с настоящим prefetch ВМ1 и задержками SRAM. Если прямой
handoff не обеспечивает чистый старт ВМ1, после commit выполняем
упорядоченный DCLO/ACLO restart, сохраняя ROM lock и содержимое SRAM.
Конкретный вариант выбираем на сквозном тесте первого этапа.

Служебные SPI/boot/CRC-регистры доступны только в boot mode.
Предлагаемое окно 177600–177656 не пересекается с клавиатурой и ядром;
после handoff оно отключается, неизвестные адреса снова дают timeout.
Защита диапазона ROM применяется после арбитража ко всем писателям.
Обычный reset сохраняет валидность ROM и RAM и сразу запускает MONIT10;
cold reset очищает валидность и повторяет чтение SD.

При ошибке SD/FAT/размера/CRC показываем этап и код ошибки на PAL и UART,
остаёмся в bootstrap. Все ожидания SD ограничены; повреждённая цепочка
FAT не должна приводить к выходу за раздел или бесконечной загрузке.

Генератор образа — адаптация `tools/make_sd.py` Пълдина:
MBR, первый FAT16-раздел 16 МиБ с начала LBA 2048,
LOADERBK.BIN и BK0010.ROM в корне. Дисковые разделы A/B не требуются.
Создание образа не должно перезаписывать существующий файл.
SHA исходных ROM и payload проверяются при упаковке и извлечении.
Запись физической SD и прошивка платы — отдельные шаги после проверки образа/JED.

## Изображение и PAL

Переносим timing, encoder, PLL и подход к строковому буферу uJ11.
Готовый `uj11_pal_video` рассчитан на другое изображение и CSR,
поэтому адресный генератор и распаковку пикселей БК делаем отдельно.
Шрифты и текст рисует исходный монитор БК в RAM;
VT-терминал и обработка управляющих последовательностей здесь не нужны.

Полный экран — 256 строк по 64 байта. Для монохромного вывода
младший бит байта идёт первым, что соответствует renderer эмулятора.
Смещение строки вычисляется как
`((SHIFT[7:0] - 0330 + y) & 0377) * 64` от базы 040000.
Регистр прокрутки передаётся в video domain согласованным mailbox;
первый вариант применяет новое значение на границе поля,
точность изменений внутри поля проверяется отдельно.

Используем 625 строк, 50 полей/25 кадров, 64 МГц, 4096 тактов на строку,
как в uJ11. `HEIGHT=256` требует нового полного теста растра.
При активном окне 3200 тактов выдача 512 точек требует 6/7 тактов
на точку, 256 цветных — 12/13. Это реализуем счётчиком фазы,
с проверкой точного числа пикселей и границ первой/последней точки.
256 строк повторяются в двух полях; это выбранный PAL-транспорт
из uJ11, а не заявление о точном воспроизведении оригинального растра БК.

5 октября положение окна исправлено по фотографиям LCD: 718…3917 тактов,
32…287 и 345…600 строк. Это сдвиг на 8 монохромных точек влево и 4 строки
вниз. Предвыборка DMA следует новому окну; 512×256 точек сохраняются.
Fast-тест проверяет все края и пять стадий монохромного DAC; пользователь
подтвердил, что загрузчик и BASIC полностью помещаются на экране.

DMA читает 32 слова на строку. Два буфера хранят по 64 байта,
следующая строка загружается заранее. При 50 полях потребление
составляет 819200 байт/с. Для контроллера с интервалом 10 тактов
на слово и clock 24 МГц идеальная загрузка строки занимает 13,33 мкс;
арбитраж и мост CPU могут увеличить это время, поэтому предельный
срок подтверждаем тестом при непрерывном трафике CPU.
При underrun гасим целую строку, сохраняем синхронизацию и фиксируем ошибку.

Цветной режим распаковывает пары бит той же памяти в фиксированные
четыре цвета БК. Выбор BW/COLOR относится к выходному тракту,
не добавляет выдуманный гостевой CSR. У локального эмулятора нет
цветного renderer: для него нужен отдельный эталон и проверка порядка цветов.

## Клавиатура и совместимость с эталоном

Физический приём PS/2 переносим из uJ11, а перевод set 2 в коды БК
реализуем в RTL с таблицами и состоянием префиксов/модификаторов.
Клавиатурный C-код uJ11 зависит от SERV и формирует ASCII/VT;
готовые ESC-последовательности для БК не подходят.

Исходная таблица назначений — `bk_translate_key` эмулятора:
Enter 012, Backspace 030, стрелки 010/031/032/033,
Home 023, F1–F9 — служебные коды, F10/F11 — РУС/ЛАТ,
Alt — АР2 с отдельным вектором 274. Esc — СТОП.
Shift/Ctrl, оба Alt, Caps Lock, make/break и автоповтор проверяем отдельно.
Русские символы формирует драйвер ROM; в DATA передаём код БК,
а не UTF-8. Для русской раскладки на обычной PS/2 фиксируем таблицу
физических клавиш и проверяем результат с MONIT/BASIC.

FIFO сканкодов и CLOCK inhibit сохраняют порядок ввода.
Непрочитанный DATA не перезаписывается новым событием.
Ready снимается чтением DATA; вектор и событие удерживаются корректно
до подтверждения CPU. Проверяем запрет/разрешение IRQ, последовательность
IRQ ACK и DATA read, одновременно пришедшую клавишу и reset.

В эталоне есть упрощения, которые нельзя незаметно перенести в аппаратный БК:

- `bk_hw_handle_key` заменяет непрочитанный DATA; исходное руководство
  требует дождаться чтения предыдущего кода.
- Renderer в РП выбирает 070000–077777 и повторяет 64 строки
  по всей высоте. Документация задаёт четверть экранного ОЗУ;
  расположение активной области и гашение нужно уточнить отдельным тестом.
- Эмулятор возвращает записанный latch 177714; у машины входной
  и выходной регистры параллельного порта раздельные.
- Bit 6 чтения 177716 привязан в эмуляторе к доступности DATA,
  поэтому состояние при удержании/отпускании клавиши проверяем отдельно.
- Встроенные CSR и таймер CPU эмулятора и vm1_wb требуют
  сверки; расхождение само по себе не доказывает ошибку RTL.

Обычный запуск, медленный ввод, полный экран и прокрутку сравниваем
с локальным эмулятором. Для перечисленных границ составляем
явные ожидаемые результаты и фиксируем выбранное поведение.
Эталонный эмулятор в рамках подготовки плана не изменялся.

## Порядок реализации и критерии готовности

| Этап | Работа | Критерий завершения |
|---|---|---|
| 1 | Vendor ВМ1А, адаптер регистров/шины, reset, CPU clock/мост, тестовая RAM/ROM, перенос MACRO-11 bootstrap ABI | Ядро стартует после DCLO/ACLO; реальные инструкции, byte lanes, RMW, timeout, IRQ и таймер проходят тесты; ROM-boot стенд запускается |
| 2 | EBR bootstrap, SPI, программный SD/FAT16, LOADERBK.BIN, BK0010.ROM, CRC/readback/lock/handoff | Настоящий ВМ1 загружает оба ROM с модели SD; нормальная/фрагментированная цепочка, SDSC/SDHC, повреждения и warm reset проверены |
| 3 | SRAM-контроллер и арбитр, PAL 512×256, scroll/РП, PS/2 → DATA/IRQ, звук, кнопка частоты и индикатор | MONIT/BASIC выводят Ok; PS/2 вводит PRINT 2+2 и получает 4; кадр совпадает с эталоном; короткая кнопка меняет режим и число; нет потерь ввода/underrun при нагрузке |
| 4 | Четыре цвета, калибровка 3 МГц и проверка повышенных частот, LPF/PLL, Diamond MAP/PAR/TRACE, экспорт | Проверены цветовые пары, границы и переходы частоты; итоговые ресурсы помещаются; timing и внешняя SRAM/SD/CDC проходят во всех включённых режимах |
| 5 | Физическая SD, JED, запуск и длительная проверка платы | Холодная загрузка ROM с SD, тёплый reset без повторной загрузки, PAL/PS/2/BASIC/СТОП/звук и переключение частоты с индикацией работают на экземпляре платы |

На этапе 1 сначала разбираем неудачный пробный старт Verilator,
а не считаем его завершённой проверкой ROM. Сравнение инструкций с
эталоном ограничиваем общим набором ВМ1А, исключаем MUL/DIV/MMU/FPP.
Для скорости нужны регистровые циклы, копирование памяти, WAIT/IRQ
и таймер при включённом/выключенном видео.

Сквозные тесты запускают настоящий CPU и загрузчики, модель SRAM
с задержками и SPI-модель SD. Нельзя заменять программный FAT/ROM-loader
готовым содержимым памяти в тесте, заявленном как cold boot.
Проверка vendor EBR использует официальную модель Lattice.
Физическое видео проверяем на телевизоре; измерение уровней ЦАП
под нагрузкой 75 Ом и читаемость 512 точек остаются аппаратными проверками.

## Структура нового проекта

Реализованная структура:

```text
bk0010-01-fpga/
  PLAN.md
  README.md, Makefile
  vendor/cpu11/           закреплённые исходники и лицензия
  rtl/                   шина БК, CSR, видео, клавиатура, bootstrap ports
  boards/hardware-lcd/   top-level, PLL, LPF, настройки Diamond
  firmware/boot/         первичный ROM на MACRO-11
  firmware/loader/       второй этап LOADERBK.BIN
  tools/                 сборка, ROM bundle, образ SD, экспорт и отчёты
  tests/                 CPU, устройства, SD bootstrap, кадры и интеграция
  research/              результаты предварительной проверки
  build/                 воспроизводимые локальные результаты, вне Git
```

Переносимые модули и инструменты сохраняют manifest происхождения.
Пълдин и uJ11 остаются исходными проектами: новая сборка не должна
зависеть от их изменяемых каталогов build или абсолютных локальных путей.
Для C/C-header соблюдаем корневой AGENTS.md: K&R, tabs 8,
braces и длина строки до 120; чужие файлы целиком не переформатируем.

## Что уже проверено и что ещё предстоит

- Eagle exporter подтвердил три пары SCH/BRD и 432 вывода FPGA;
  сгенерированные таблицы актуальны.
- Все четыре файла vm1_wb элаборируются Icarus. Простой реальный
  поток MOV R0,R1 исполняется; установившийся интервал в модели
  с мгновенным ACK — 6 периодов vm_clk_p. Это не режим 3 МГц БК.
- PS/2 transport прошёл 24 проверки; SRAM — 37; PAL encoder —
  33834 отсчёта; общая модель строковой EBR — 1024 адреса.
- Эталонный C-эмулятор загрузил BASIC и выполнил PRINT 2+2 → 4.
  Сохранены [стартовый экран](research/reference-boot.png)
  и [результат команды](research/reference-print.png).
- SPI ABI Пълдина прошёл RTL-тест; генератор FAT16 — roundtrip
  и проверку отклонения некорректной геометрии/BPB.
- Контроллер кнопки uJ11 прошёл 28 проверок. Сканер индикатора прошёл
  48 проверок полного кадра/заполнения и 192 проверки сброса в разных фазах,
  с непрерывным контролем единственного выбранного сегмента.
- Реализованы clock divider 3/6/12/24 МГц, deferred switch на свободной шине,
  Gray synchronizers и индикация применённой частоты. `tb_panel.v` проверяет
  периоды/фазы, переключения, ожидание завершения транзакции, wrap и длинный reset.
- Причина старого Verilator-стенда выявлена: wildcard X в аргументе функции
  cmp теряет маску в двухсостоянийной модели. Неизменённый vendor PLM преобразуется
  в явные bit masks. Icarus подтвердил эквивалентность ВМ1А/ВМ1Г на 44 768 парах.
- Настоящее ядро ВМ1А загрузило MONIT10/BASIC10 и выполнило `PRINT 2+2`.
  Обе 16-КиБ VRAM-копии совпадают с C-эмулятором побайтно.
- Native cold boot с resident EBR, bridge и SD SPI прошёл SDHC, SDSC-v1 и
  фрагментированный ROM. Все 32 КиБ ПЗУ и стартовая VRAM совпадают с эталоном.
  Тёплый reset сохраняет lock/ПЗУ и не выполняет новые чтения SD.
  Повреждения MBR/BPB/header/FAT/payload/SRAM отвергаются с ожидаемым кодом.
- Физический PS/2 с новым BK decoder прошёл make/break, Shift/Caps/Ctrl/Alt,
  стрелки, STOP, Pause, parity fault и backpressure. CDC-тест проверяет byte lanes,
  RMW с удержанием CYC, удержание ACK, cancellation и reset.
- Новый PAL с физической моделью SRAM и постоянной CPU-конкуренцией прошёл
  3 276 800 отсчётов пикселей для каждого из моно/цвет режимов, четыре поля,
  scroll/RP и намеренное starvation. Полный SoC также прошёл cold/warm boot
  через физические модели SRAM/SD, PS/2 PRINT 2+2, live frequency switch,
  PAL без underrun и побайтную сверку ROM/VRAM; стенд — `make test-soc`.
